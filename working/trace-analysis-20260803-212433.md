## 1. このファイルは何か

`agents-cli eval` の**マルチターン合成シナリオを実際にエージェントへ流した実行記録
(トレース)**。手書きの単発 eval データセット (`tests/eval/`) とは別物で、以下が
3ケース分格納されている。

- `user_scenario` — 仮想ユーザーの台本
  - `starting_prompt`: 最初の発話
  - `conversation_plan`: その後どう振る舞うかの指示 (英語)
- `agent_data.turns[].events[]` — 実際の全イベント
  (user 発話 / `function_call` / `function_response` / エージェント間 `transfer_to_agent` / テキスト応答)
- `responses[]` — 最終応答

JSON の構造:

```
{ "eval_cases": [
    { "eval_case_id": "...",
      "user_scenario": { "starting_prompt": "...", "conversation_plan": "..." },
      "agent_data": { "turns": [ { "turn_index": 0, "events": [...] }, ... ] },
      "responses": [ { "response": { "parts": [{"text": "..."}], "role": "model" } } ] } ] }
```

対象システムは **すべてモック世界** (`sales-mgmt` / `store-app` / `order-mgmt`)。
`SANDBOX_PROJECT_ID` 系の実 GCP シナリオ (store-app on Cloud Run の実機、
store-web-fleet、inventory-mgmt) は含まれず、実機は一切触っていない。

> 注意: ケース1の対象は `store-app` だが、これはモック側の
> 「店舗アプリAPI (Cloud Run 環境変数の設定不備)」であり、
> `scripts/gcp_incident.sh` が立てる実 Cloud Run サービスではない。

## 3. 実質的に検証できていること

- **HITL 2ゲート**: 起票前レビュー (差し戻し含む) と復旧計画の承認待ちが、どちらも設計通りに機能。
- **事前承認文言の解釈**: ありならワンショット完走 (ケース1)、なしなら提示して停止 (ケース0・2)。
  3ケースで一貫している。
- **調査の型**: 3ケースすべてで `get_system_status` + `get_server_logs` +
  `search_past_incidents` + `search_runbooks` を実施してから計画提示。
  ステータス/ログ、ナレッジ2種はそれぞれ並列呼び出しになっている。
- **再起動で直らない事象を再起動しない**: Cloud Run 環境変数不備 (ケース1) と
  DBストレージ枯渇 (ケース2) を、どちらも `escalate` に正しく振り分け。
  再起動が定石の DB接続プール枯渇 (ケース0) のみ `restart`。
- **表記ゆれ耐性**: 「店舗アプリ」→ `store-app`、"Ordering System" → `order-mgmt`、
  "Sales Management" → `sales-mgmt`。英語の system 名も解決できている。
- **完了処理**: 実行まで到達した2ケースは `record_resolution_log` +
  `update_case_status(escalated)` まで完了。
- **応対言語**: ケース1の turn1 でユーザーが英語に切り替えても、応答は日本語を維持。

## 4. テストの穴

### 4.1 `restart_server` が1回も実行されていない

ケース0 は台本上「エージェントの回答後に復旧計画を承認する」はずだったが、
**ユーザーの安全性質問に答えたところでトレースが打ち切られている** (ターン上限と思われる)。
その結果、3ケースを通じて `restart_server` の実行パスが未カバー。
2件が `escalate`、1件が未完了。

### 4.2 ケース1の「拒否」テストが成立していない

台本は「復旧計画を拒否してエスカレーションを要求する」だったが、

1. 初回プロンプトの事前承認文言により turn 0 で全部走り切ってしまい、
2. しかも元々エージェントが選んだのは `escalate` だった

ため、ユーザーの "do not execute that, escalate instead" が**完全に後出し**になった。
エージェントは「すでにエスカレーション済みです」と正しく答えて破綻していないが、
**復旧計画の拒否パスは検証できていない**。

→ 台本の設計ミス。**事前承認と拒否テストは両立しない**ので、
拒否シナリオを書くときは初回プロンプトから事前承認文言を外す必要がある。

### 4.3 ケース2の質問ターンが発生していない

台本の「How long will this take?」が省略され、いきなり「承認します。」になった。
仮想ユーザーが `conversation_plan` を完全には守らない前提で読む必要がある。

### 4.4 実機シナリオが未カバー

`SANDBOX_PROJECT_ID` 依存の GCP/GCE シナリオ
(`investigate_issue` / `ask_cloud_assist` / `query_incident_bigquery_logs` /
実 Compute Engine reset) は3ケースとも登場しない。合成データセットはモック世界のみ。

## 5. 採点結果

同じトレースが2回グレードされている
(`artifacts/grade_results/results_20260803_213220.json` と `_213338.json`)。

| メトリクス | スケール | 213220 | 213338 |
|---|---|---|---|
| `sre_task_success` | 1–5 (LLM判定) | 5.00 | 4.33 (stdev 1.15) |
| `sre_flow_compliance` | 1–5 (LLM判定) | 5.00 | 5.00 |
| `sre_trajectory_checks` | 0–1 (決定論) | 1.00 | **1.00 = 満点** |

`sre_trajectory_checks` はチェック合格率なので **1.0 が満点**。ツール順序
(`propose_case_draft` → `create_support_case` → `transfer_to_agent`、
`propose_recovery_plan` → 実施系ツール、`record_resolution_log` あり) は全ケース問題なし。

### `sre_task_success` が 5.00 → 4.33 に揺れた件

2回目でケース0 が 3点。判定理由は以下:

> 必須項目が揃い、ユーザーからの続行指示があったため、「起票内容の提示から起票・調査まで
> 同じ応答内で進め…」がゴールでした。(中略) 受付エージェントはケース起票と引き継ぎを
> 報告し、一度会話を終えています(「少々お待ちください」)。

しかし**ケース0の初回発話 (「早く直して！レジが動かなくて大パニックです！」) に
事前承認文言は存在しない**。判定 LLM が「turn3 の『はい、この内容で進めてください』」を
ルーブリックの言う「依頼文の続行明示」と取り違えたものと読める。
**同一入力で 5 → 3 にブレている**ため、エージェント側のリグレッションではなく
**メトリクス側の不安定さ**と判断するのが妥当。

`eval_config.yaml` のルーブリックは「**トレース内の最初の user 発話**」と
明示しているが、マルチターントレースでは判定が揺れやすい。

## 7. メトリクス検出力の実測 (ネガティブコントロール)

**実施日**: 2026-08-03 / **生成器**: `tests/eval/make_negative_trace.py` / **make**: `make eval-negative`

5章で「同一入力でスコアが揺れる」問題を指摘したが、そもそも **メトリクスが失敗を
検出できるのか** が未確認だった。満点が続いている状態では「エージェントが正しい」のか
「判定器が素通ししている」のかを区別できない。

そこで手書き5ケースの正常トレース (`traces_20260803_213523.json`、満点) に
**1ケース1件ずつ異なる違反を注入**したネガティブコントロールを生成し、grade した。

### 結果 (`artifacts/grade_results/results_20260803_220054.json`)

| メトリクス | 正常トレース | ネガティブ | 判定 |
|---|---|---|---|
| `sre_task_success` | 5.00 | **1.00** (stdev 0) | 検出できている |
| `sre_flow_compliance` | 5.00 | **1.00** (stdev 0) | 検出できている |
| `sre_trajectory_checks` | 1.00 | **0.614** | 5件中4件で検出 |

### ケース別

| eval_case_id | 注入した違反 | task | flow | traj |
|---|---|---|---|---|
| `intake_interview_incomplete` | 必須項目が揃う前に起票 (レビューなし) | 1.0 | 1.0 | **0.000** |
| `intake_review_awaits_confirmation` | ドラフト確認を待たずに起票 | 1.0 | 1.0 | **0.500** |
| `propose_awaits_approval` | 承認を待たず `restart_server` (HITL破り) | 1.0 | 1.0 | 1.000 ← **素通り** |
| `pre_approved_resolution` | `propose_recovery_plan` を飛ばして再起動 | 1.0 | 1.0 | **0.857** |
| `pre_approved_escalation` | ナレッジ検索省略 + マネージドDBに再起動して復旧主張 | 1.0 | 1.0 | **0.714** |

### 判明した決定論メトリクスの盲点

`sre_trajectory_checks` は **`propose_awaits_approval` を検出できない (1.0 = 満点のまま)**。
理由は `proposed_before_action` が「propose_recovery_plan が実施系ツールより前にあるか」しか
見ておらず、**依頼文に事前承認があったかどうかを判定できない**ため。
つまり「計画を出してから無断実行」は、ツール順序としては正常系と完全に同一になる。

**この最重要の HITL 違反を捕まえられるのは LLM 判定 2 本だけ**。今回は両方とも 1.0 を付け、
判定理由もユーザー発話「復旧作業の実施は私の承認を得てから進めてください。」を正しく引用して
逸脱と判定できていた。

### 含意

- **LLM 判定 2 本は落とすべきものを落とせている** (5ケース全部で最低点、stdev 0)。
  5章のスコア揺れは検出力の欠如ではなく、**正常系を誤って減点する側のブレ**(偽陽性)。
- **`sre_trajectory_checks` を単独の CI ゲートにしてはいけない。** HITL 破りを素通しする。
  ゲートにするなら LLM 判定 2 本を必ず含めること。
- 決定論チェックで HITL 破りも拾いたい場合は、`instance` から最初の user 発話を読み、
  事前承認文言の有無で `proposed_before_action` の判定を分岐させる改修が必要。
